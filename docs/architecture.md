# Workflow foundation: architecture and boundaries

## Implemented boundary

The standard-library Python package `agent_lab` owns local SQLite-backed workflow state, a controlled text-file broker, scoped candidate experience memory, a DeepSeek protocol adapter, a model-facing tool gateway, an opt-in Docker Python executor, and a cooperative multi-agent scheduler. Its public API is called by a trusted local application. A bounded runner executes one assigned task; the scheduler advances eligible delegated tasks across configured roles. There is no server or authenticated user session, and live-model autonomous planning/negotiation has not been demonstrated. Actual Python execution requires the explicit Docker backend; there is no host-code fallback. Opening the database or raw workspace paths directly bypasses application checks; protect them using normal operating-system access controls. Tests use temporary directories and demos use fresh ignored run directories.

The tool gateway keeps identity, transition authority, and completion validation outside model-controlled arguments. Never expose `register_actor`, `respond`, or arbitrary passing `checks` as tools a model can call to impersonate a user or certify its own result.

## Durable records

- Actors have an immutable human/agent kind. Registration is a trusted setup operation.
- Conversations have explicit membership. A private chat has exactly one human and one agent; group chats contain human and agent participants. Reads and writes check membership.
- Tasks belong to a conversation, have an assigned agent, and may reference a parent. An assigned agent can create child work for another participating agent while the parent is running. The scheduler routes these delegated assignments to eligible configured roles; live autonomous role negotiation remains unvalidated.
- Human requests record a prompt, the addressed human, response, and optional canonical action/digest. SQLite transactions commit each state change together with its audit event.
- Audit events record task creation, delegation, start, human requests/responses, action release, completion, failure, and cascading cancellation.

## State and human-response rules

Tasks begin pending and can start only through their assigned agent. Running tasks may await clarification or approval. Only the addressed human can reply once; a valid clarification or approval resumes the same task. Denial cancels the task and all unfinished descendants. A failed parent also cancels unfinished descendants. Completed tasks cannot be restarted or rewritten.

Approval is bound to the canonical JSON representation of an exact action, including all supplied arguments. A changed branch, commit, or other argument invalidates the match. A request is usable only in its resumed task revision; a later human request makes older approvals stale. Action release is transactional and at most once, including across multiple database connections. A task cannot succeed while its current approved action remains unreleased.

**Release is not external execution.** A future executor must take the exact returned action and execute it with the applicable sandbox and resource checks. An approval does not grant authority the human does not already possess. Authenticated identity, tool-specific permission, expiry, and resource-scope enforcement must be added at that boundary. There is no permission-management service in this foundation.

At-most-once release does not guarantee exactly-once effects. A process may crash after consuming approval and before or after the external action. Do not replay the effect automatically: reconcile the external state and obtain a new applicable approval when needed. Similarly, cancellation cannot undo an already released/in-flight effect. Future tools need idempotency or explicit reconciliation.

## Completion and accounting

Only the assigned agent may finish a task. Success requires a running task; a trusted failure may also terminate a task awaiting human input/approval, close its wait interval, and cancel descendants. Success requires a nonempty map of named passing checks supplied by a trusted caller or computed by a trusted verifier inside the task-state transaction, and every direct child must have succeeded. Failure requires a reason. The scripted workflow demo reads its fixed note back before passing its checks. `FileTools.complete_from_text` hashes actual file bytes against trusted expected UTF-8 text within the transaction. Missing or mismatched artifacts cannot complete the task. Expected text and verifier callables must never come from model-controlled arguments. This exact-text verifier is not a general verifier for arbitrary tasks or code-test results; accepting model-provided passing booleans would not satisfy that requirement.

Goal and subtask status fractions are reported separately. Failed, cancelled, pending, and waiting assignments are not counted as successful or silently removed from the denominator. Elapsed time runs from assignment to terminal state, including time awaiting a human. Human waiting is also recorded separately, including an open wait, and survives restart. Wall-clock durations assume a reasonably stable system clock; this is not a distributed-clock protocol.

Offline reports explicitly identify themselves as fixtures, make zero model calls, and are not valid model-performance benchmarks. The provider parser can return reported token counts and actual response/model IDs, but no live usage, model-call timing, or learning improvement has been measured yet.

## Candidate experience memory

`ExperienceMemory` stores each agent's candidate suggestions in SQLite with separate source observations. Capture requires an assigned task to have ended in a success or failure with a terminal event and trusted recorded checks/error. Source snapshots include that event, outcome evidence, and any actual artifact-verification records. A trusted-caller success without artifact records is distinguishable from an artifact-verified outcome. Capturing a completed outcome does not prove that the accompanying suggestion is correct or that a suggested fix caused the result; every lesson remains explicitly `candidate`.

Retrieval/selection requires the agent's assigned running task. Memory is scoped by **owner agent, conversation, and explicit namespace**. Private-chat content is therefore not automatically surfaced in group tasks; development and fresh evaluation namespaces do not share candidates. Actor IDs still require a future authenticated transport. Cross-conversation reviewed sharing is not implemented. An eventual evaluation controller must choose memory scope/reset rules from the instructor's protocol; do not move development observations into held-out inputs to improve scores.

Retrieval uses deterministic Unicode word overlap with cosine normalization and condition tags, without embeddings, model calls, or semantic inference. Scores indicate lexical relevance only, not reliability or causal effectiveness. Returned candidates include their source snapshots and observed reuse counts. Source/candidate digests detect accidental corruption; they are not signatures protecting a database from a hostile host with write access. This memory helper is not an internet-search tool or an autonomous retrieval agent.

A candidate must be retrieved in the current task before it can be selected once. After that task terminates, the trusted caller records its observed success, failure, or cancellation. Unassessed uses remain visible. Assessment is idempotent and never promotes a candidate to a proven fix or grants an action approval. Retrieve/select cannot resume a paused task, authorize a tool, execute advice, or certify completion. A future model may consider retrieved text only as reference data within its current task and permissions.

Only exactly matching lesson text and normalized tag sets are deduplicated, preserving every distinct source task and both successful and failed outcomes. There is no automatic semantic merge. Retirement excludes a candidate from future retrieval while preserving its sources and use history; recapturing a duplicate does not silently reactivate it. Each owner/conversation/namespace has a hard cap of 1000 total candidates, including retired records. Source/use history has no separate retention quota yet; it remains private runtime data and is excluded from commits.

The `memory-demo` fixture deliberately separates plumbing from efficacy: the first text check genuinely fails, but fixture code explicitly writes the second correct output. Its recorded subsequent success and duplicate merge do not establish a learning gain. Formal memory-on/off comparisons on new tasks with the allowed model remain required.

## Checks and remaining work

### Controlled file API

`FileTools` binds one private, current-user-owned file root to the workflow database by its filesystem identity. Each task has a separate directory and only its assigned agent may operate on it while running. This is stronger than filename conventions within the broker API, but it does not restrict a process that bypasses the broker. Untrusted code must not run on the host or receive broker descriptors.

File paths must be relative POSIX paths without empty, dot, dot-dot, backslash, or NUL components. Directory traversal uses anchored descriptors and no-follow opens. Reads/updates/deletes require regular single-link files, reject symbolic/hard links and special files, validate UTF-8, and enforce a configurable byte limit. Creates never overwrite; updates/deletes require the expected prior SHA-256. Updates replace through a temporary file in the same directory. Broker operations produce task audit events and content receipts. The default file limit is one MiB. Unsupported OS descriptor operations fail closed; Windows is not currently supported by this broker.

Explicit handoff copies the offered text into a stored snapshot and records a manifest binding its source, recipient task, digest, and byte count. Only the designated assigned recipient can import it once, into a fresh path in its own task directory. Source and recipient must share a conversation; a failed/cancelled source cannot supply its snapshot. Recipient import verifies snapshot integrity. Future source edits do not change an existing offer. This is application-level transfer, not direct cross-workspace access or autonomous negotiation.

SQLite serializes cooperating broker operations and task transitions. Filesystem effects and SQLite commits are not a single atomic transaction: a crash can leave an unrecorded file or orphan snapshot. Inspect content and reconcile before retrying; do not assume the audit log proves the absence of a disk effect. Same-user hostile host processes and OS-level file access are outside this broker's boundary. No storage/retention quota for the number of files or snapshots is implemented yet.

The legacy `FileTools.execute_code` entry point always refuses host execution. Actual isolated Python execution uses the separate explicitly configured `DockerPythonExecutor`/`run_python` path described below. No host subprocess fallback, network operation, model call, or Git operation is hidden behind it. File ownership checks are not evidence of satisfying the full sandbox requirement.

Behavior checks cover conversation access, delegation ownership, parent/child completion, restart/resume, wrong-user responses, exact-action approval, stale and duplicate release, concurrent release, denied/failed parent cancellation, and accounting. The fixture additionally checks that existing run directories are not overwritten.

Additional checks cover controlled file CRUD, ownership and path escape attempts, symlink/hard-link/special-file rejection, stale digests, corrupted/duplicate/concurrent handoff, restart, mismatched completion artifacts, and refusal of unconfigured execution.

Memory checks cover provenance, owner/private-chat/namespace boundaries, duplicate source preservation, failed/cancelled/unassessed reuse, retirement, corruption rejection, restart, and the separation between reference memory and execution authority.

## Provider protocol and tool gateway

`DeepSeekClient` serializes non-streaming chat requests with an explicit model identifier and a bounded output token limit. `DeepSeekHTTP` only targets `https://api.deepseek.com/chat/completions`, requires a supplied key, and refuses network use unless the trusted caller explicitly enables it. There is no environment-key discovery, HTTP redirect, alternate-provider fallback, or automatic POST retry. Provider HTTP failures expose status codes without response bodies or authorization headers. Request/response bodies have a two MiB cap; socket timeouts are bounded but do not constitute a total task deadline. A partially transmitted/timed-out call may have been billed and must be reconciled before retrying.

The protocol follows the [official DeepSeek chat completion specification](https://api-docs.deepseek.com/api/create-chat-completion). Thinking is explicitly disabled for this first adapter; if a response includes `reasoning_content`, the assistant message retains it for protocol replay. The parser accepts one complete assistant choice ending in `stop` or `tool_calls`; truncated, filtered, malformed, duplicate-key, and inconsistent completions cannot release tools. It retains actual response/model IDs, usage counts, tool IDs, and argument strings. These fields from an injected synthetic transport remain synthetic evidence. No OpenAI/Anthropic endpoint or SDK is used. HKGAI support requires its issued interface details rather than an assumed compatible endpoint.

`ToolGateway` binds the task, agent identity, addressed human, eligible delegates, backend instances, tool allowlist, and call cap in trusted application setup. Its registered tools cover controlled text CRUD, explicit artifact handoff, child delegation, conversation messages, clarification, and candidate memory retrieval/selection. Tools absent from a role's allowlist cannot execute. Argument validation rejects missing/extra fields (including caller-supplied actor/task identity), wrong types, duplicate keys, non-finite JSON, invalid UTF-8, and oversized strings. Existing file/memory/workflow ownership checks still run at execution time. Task-bound conversation posts recheck running ownership inside the message transaction.

There is no model-facing tool for success certification, human replies, approval release, actor registration, host shell execution, internet search, or Git. Model final text leaves task status unchanged. Trusted expectations and independent checks remain outside model control. A future scheduler must preserve user constraints, validate a response's calls before sequential dispatch, stop dispatch when the task pauses/terminates, and provide applicable tool results before requesting another completion. The single-task runner now performs this serial preflight/pause handling. Multiple tool proposals do not imply parallel execution or atomic batch effects; the separate scheduler chooses eligible task turns; no live-model collaboration result is established here.

Every schema-valid dispatched proposal reserves a `(task, call_id)` record before effects. Reservations, including failed calls, count against the persisted task tool-call cap. Recreating a gateway cannot increase/reset that cap. A repeated ID is rejected across connections and restarts; it is not silently executed or returned as a new success. A crash after reservation can leave status `reserved` with an uncertain effect. Inspect the recorded arguments/results, file receipts, and actual artifacts before issuing any fresh proposal. Call IDs alone do not make two different proposals with different IDs equivalent or establish exactly-once effects. The gateway cap is not an LLM-call, token, total-time, storage, or monetary budget; the runner adds per-task model-attempt and reported-token thresholds, while the scheduler adds shared task-tree attempt/token/tool/time bounds. Strict monetary caps and hard deadlines beyond the isolated Python tool remain future work.

Deletion is the currently exposed critical action: a valid proposal first checks the exact file version, persists an approval request containing the exact tool/arguments, and pauses without deleting. A trusted human controller records the decision through `Workflow.respond`. Only its separate `release_approved` entry point can consume the matching approval and delete that version. It is absent from model tools, bound to the original task/human, and single-use. Changed content, denial, a stale approval, or an approval for another task cannot release deletion. If the file effect fails after approval consumption, inspect state and obtain a new applicable approval; do not replay automatically. New external tools must define their critical effects before registration; this deletion policy is not blanket permission for future network/Git tools.

`protocol-demo` injects two fixed HTTP-shaped responses, performs one real controlled file operation, returns its result to the next synthetic request, and verifies actual text independently. It saves a synthetic transcript and explicitly reports zero model/network calls, no process sandbox, and no benchmark validity. Offline checks also exercise protocol rejection, sanitized transport failure, disabled network, redirects, role allowlists, identities, scopes, approval, crash ambiguity, repeated/concurrent calls, and persistent call limits. No paid call was made to establish these results.

## Bounded single-task runner

`TaskRunner` repeats provider/tool turns for one already-started assignment. Trusted setup supplies an explicit fixture/live mode, the supported provider client, immutable user constraints, limits, role tools, and an optional independently written verifier with a stable version ID. The initial system prompt and structured context retain the global goal, current assignment, and all supplied constraints. The scheduler supplies the same original constraints and role-specific instructions to every descendant. Neither component automatically infers omitted constraints or validates a general dependency plan. Configuration records include the prompt digest, tools, model/output limit, human, verifier version, execution-backend image/policy, and limits. Reconstruction rejects changes instead of resetting the budget. Verifier IDs must identify the actual trusted implementation/expectations; an unchanged arbitrary label is not authentication of changed verifier code.

SQLite stores the transcript, each attempted request and normalized response, actual model/response IDs, timestamps, known usage, pauses, and human replies. An atomic `calling` reservation permits one provider attempt at a time across cooperating connections. A crash with unknown provider output remains `calling`, with unknown usage explicitly counted; `step` never resends it automatically. Expected provider errors stop the task without a retry or synthetic fallback. A late response after a trusted abort retains its usage but releases no new tools. The stored transcript contains private task data and remains excluded from Git.

Before effects, every proposed call in a response passes batch schema/ownership/replay/budget preflight. Tools execute serially and still recheck permissions. A pause/termination prevents subsequent proposals in that batch from executing; skipped calls receive explicit failure results. Clarification resumes after the addressed human replies. Approval alone does not trigger another provider request: the controller must first release/reconcile the exact action through the separate trusted gateway entry point. Human replies are taken from workflow records and appended once; the original constraints remain in context.

Final text proposes completion. With a trusted verifier, the workflow verifies and transitions under the same database transaction. `FileTools.text_verifier` builds the existing actual-text check for this purpose; do not call that callback outside the completion transaction. Named failed checks return as evaluator feedback for bounded repair. Without an automatic verifier, the runner enters `awaiting_verification` while the task remains incomplete. A trusted evaluator can reject it through `review_failed` or independently complete the task through the workflow API. These functions and success/approval controls are absent from model tools. Reports requiring human judgment are therefore not automatically certified by a model's confidence.

Per-task limits cover reserved provider attempts, reported total tokens, elapsed duration from assignment (including human waits), repeated identical proposals/outcomes, and the gateway's separate tool-call cap. Exhaustion records failure, preserves partial artifacts, and cancels unfinished descendants; it does not remove the run from the completion denominator. Reported tokens can overshoot their threshold within the response that reveals usage; the runner then releases no tools or further provider attempts. Unknown usage is not assumed to be zero. These per-task thresholds are not a strict monetary budget; a configured scheduler additionally enforces shared parent/child limits as described below. Duration is checked at boundaries and after verification; socket IO and trusted callbacks are not forcibly interrupted. The Docker executor adds a bounded subprocess/container lifetime and resource limits for its code tool; provider IO and arbitrary trusted verifier callbacks still need separate hard supervision. `run` creates no background worker or timer: an expired paused task is finalized on its next controller invocation. Wall-clock stability remains an assumption.

Exact repeated request/outcome signatures detect a narrow class of unproductive repetition even when tool call IDs differ; changing the proposal can evade this heuristic but not the attempt cap. It is not a general semantic progress detector. Recovery is also explicit: after the prior worker has stopped, `recover_tools` can reconstruct committed tool results from the current turn and mark unstarted calls skipped without executing them. Results from earlier turns cannot be attributed to a new turn. A `reserved` tool with no committed result, interrupted verification, or unknown provider response requires trusted inspection/reconciliation or `abort`; it is never automatically replayed. This API does not replace process ownership, authentication, or a worker lease service.

`runner-demo` supplies three scripted protocol responses and a scripted human answer, closes/reopens the database at clarification, creates a real controlled file, and performs independent text verification. Its synthetic call/token metadata is labelled fixture data; it records zero actual model/network calls and no benchmark validity. Tests additionally cover bounded verification repair, preserved constraints, all-or-no-effects schema preflight, pause/approval handling, attempt/tool/token/time limits, repeated failures, unknown/late provider outcomes, recorded versus uncertain effects, and concurrent attempt reservation.

## Cooperative multi-agent scheduler

`MultiAgentScheduler` owns one root task and a persisted configuration of eligible `Role`s, the addressed human, user constraints, clients, and a versioned trusted acceptance factory. All roles use the same explicit allowed-model identifier, with distinct instructions, tools, and delegation eligibility. A provider response chooses whether/what/whom to delegate through the existing gateway. The scheduler does not prescribe a coordinator/retriever/coder sequence. Specialist-to-specialist and self-delegation use the same checked child-task path; both count toward shared limits. This is infrastructure for model-driven allocation, not proof that a live model negotiates roles effectively.

Configure the scheduler on a fresh pending/running root **before** runner/tool execution or child creation. `TreeLimits` defaults are 16 total tasks (including completed/failed assignments), depth 4 below the root, 48 reserved model attempts, 128,000 reported tokens, 128 reserved tool calls, and 900 seconds from root assignment including human waiting. Role-specific `Limits` and tool-call caps also apply. These are implementation defaults, not instructor requirements. Budgets persist independently of controller objects and cannot be reset on reconstruction. Existing standalone runners cannot be retrofitted into a fresh budget that hides prior calls.

Each `step()` claims the controller in SQLite, advances at most one eligible task turn, then releases the claim. The current policy is deepest-task-first, creation-order among equal depths, with one turn per invocation and no background worker. Parent runners yield without spending another model attempt while children remain incomplete. Every active task's deadline, including waiting ancestors, is checked before choosing work. Human-waiting, approval-release, and independent-review tasks yield explicit blockers while ready siblings can proceed. `run()` stops when the root terminates or no further work can proceed. The next invocation finalizes expired waits; there is no timer service.

The trusted `verifier_factory(task)` returns `(callable, stable_version_id)` or `None`. A dynamically delegated task for which the application has no independent acceptance rule therefore awaits trusted review; it does not succeed merely because a model says done. The root's `acceptance_id` versions this application policy. The callable/expectations remain outside model tools; unchanged IDs do not authenticate altered application code. Failed automatic checks feed evidence back for bounded repair within the same task. A terminal failed/cancelled child currently fails the root and cancels its unfinished descendants, retaining artifacts and evidence. Automatic plan revision, replacing failed dependencies, reassignment, and a general dependency DAG remain future work.

Before a parent reserves its next model attempt, each terminal direct child is appended once as a `child_task_result` containing assignment, assignee, state, trusted recorded checks/error, and metadata for snapshots explicitly offered **to that parent**. It grants no permission. The parent must use `accept_artifact` to obtain a task-local copy and still pass its own acceptance checks. No raw child transcript, private memory, unoffered files, or other conversation is copied. The child receives its own task/parent/root IDs for explicit handoff. Reports or final text requiring review must be delivered through artifacts and a suitable trusted acceptance policy; this is not a universal report-quality verifier.

Shared guards run at existing transactional boundaries: model-attempt reservation, tool-batch preflight, actual tool reservation, child creation, approval consumption, and successful completion. A child cannot obtain a fresh aggregate budget by delegating or restarting a runner outside the scheduler. Late/aborted responses still add reported usage. Batch preflight reserves nothing; concurrent dispatch rechecks the counters before effects. These budgets do not forcibly stop provider IO or arbitrary trusted callbacks. Reported tokens can overshoot when a response reveals usage, and an interrupted reserved attempt has unknown usage, so these are **not strict billing caps**. Live status reports reserved attempts, with `model_calls: null` rather than claiming an exact external-call count; fixture calls remain zero.

A persisted controller claim prevents a second cooperating controller from advancing the same goal. A killed process can leave that claim held. After confirming the prior worker has stopped, a trusted operator may call `recover_controller()` to clear only the claim. A `calling`, `processing`, or `stopping` runner still blocks the task tree pending inspection. Use the runner's existing `recover_tools()` only for committed current-turn effects; never replay an unknown provider request or a reserved tool. `scheduler.runner(task_id)` gives trusted access to review/reconciliation within this root; these controls are not model tools. The claim is not authentication or a distributed lease with automatic expiry. Direct trusted application callers must obey the controller ownership contract.

`scheduler-demo` uses fixed synthetic responses to delegate coordinator → writer → editor, clarify with a scripted human answer, close/reopen SQLite, offer/accept actual snapshots through both parents, and independently verify every note. Its report marks zero model/API calls, no code execution, no autonomous-model collaboration evidence, and `benchmark_valid: false`. Tests also cover waits/review with ready siblings, inherited constraints/private context boundaries, failure propagation, scope separation, shared limits across tasks/connections/restart, batch preflight, expired approval/verification, and interrupted controller/provider/tool recovery. No live-provider, sandbox, negotiation-quality, learning-gain, or official-test-set result follows from this fixture.

## Isolated Python execution

`DockerPythonExecutor` runs exact task-owned source/text snapshots in a fresh Linux container selected through an explicit local Unix socket and a content-pinned official Python image. It never invokes generated code on the host, forwards host credentials, shares host folders, mounts the Docker socket, pulls an image, or starts a VM automatically. An empty private Docker CLI configuration and a small host environment keep existing contexts/proxies/credential helpers out of the invocation. The backend verifies engine limits/seccomp and the container policy before starting code. Its persistent database binding prevents changing the endpoint or engine identity to falsely confirm an old run's cleanup.

Untrusted Python uses UID 65534. The trusted watchdog and exporter use a separate UID 65533, with capabilities dropped and no new privileges. The image is read-only; only bounded scratch tmpfs mounts are writable. External networking is disabled and memory, CPU, processes, files/inodes, output, and execution time are limited. The host streams bounded IO and removes the run-labelled container on interruption; a separate fixed-lifetime container watchdog also stops it if the host loop disappears. A restricted container relies on the trusted Docker/Linux kernel/image and is not an unconditional security guarantee.

`run_python` is registered only with an explicit backend and role allowlist. Its bounded job contains an entrypoint, exact input-file hashes, script arguments, and declared new text output paths. Models cannot set the image, socket, host mounts, privileges, or limits. Every input passes existing file ownership/path/version checks. Actual exit code, interruption, bounded stdout/stderr and byte hashes, image/engine identity, duration, output receipts, and cleanup state are recorded. A tool returning normally does not certify the program or goal: final success still needs independent acceptance evidence.

Export reads only declared bounded, regular single-link UTF-8 files through no-follow descriptors; pipes, symlinks, binary data, and oversized results are rejected. Validated text snapshots/digests are checkpointed before removal, then imported through task-owned create-only file operations. Effects and database/file commits are not one atomic transaction. Failed cleanup blocks another sandbox in that workflow until trusted `reconcile_cleanup`; `recover_exports` can restore checked snapshots without code replay or overwriting changed artifacts. These recovery controls are not model tools. Immediate cleanup cannot be confirmed while the daemon is unavailable; retain uncertainty and recheck after access returns.

Real-container checks exercise multi-file tests/export, actual assertion failure, host/agent workspace and credential-environment separation, network/root-write refusal, UID/capability/seccomp/cgroup policy, time/output/memory/PID limits, descendant cleanup, unsafe exports, cancellation, and independent watchdog expiry. Offline fake-engine tests separately exercise policy tampering, scoped cleanup, durable export recovery, and changed engine identity; those mocks are never a runtime fallback. [Sandbox setup and validation](sandbox.md) documents exact commands and limits. Each execution is fresh and only one sandbox is active per workflow database; persistent per-agent containers, broader dependencies/languages, and concurrency remain future extensions. This validates a process boundary, not model ability or the instructor's yet-unconfirmed minimum isolation standard.

## Terminal control center

`agent_lab.tui` is a trusted local interface. `controller.ControlCenter` imports no Textual code: it owns one backend thread that creates and exclusively uses the SQLite connection, file broker descriptors, memory, and schedulers, so connection thread ownership stays correct and Textual thread workers wait on futures instead of blocking the event loop. Long scheduler steps therefore serialize other backend calls; the UI stays responsive but shows results when the step finishes. All state changes go through existing APIs: `create_chat`, `post_message`, `create_task`, `respond`, `MultiAgentScheduler.run`, `ToolGateway.release_approved`, and `TaskRunner.review_failed`/`finish_task` for trusted human review. Posting a message never creates or executes a task.

Read views come from `queries.WorkflowQueries`, which applies the workflow's conversation-membership rule and never writes. Request status distinguishes *pending*, *answered*, *denied*, *granted awaiting release*, *granted but stale*, and *released*; a released action's outcome is the next recorded effect event (for example `file_deleted`), or `unrecorded`, which is reported as uncertain and never retried. Uncertain views also list interrupted runner turns, reserved tool calls, and held scheduler claims. Display strings redact credential-like keys/values and bound long text; redaction is presentation only, not a storage control.

`inspection.ArtifactInspector` adds one new access path: a **human member** of a task's conversation may read (never write) task-local text and offered snapshots through the broker's descriptor-anchored no-follow reads. Agents cannot use it, it cannot reach paths outside the broker root, and listings come from broker receipts, so an unrecorded disk file is not listed while a changed recorded file is flagged. Version comparison covers recorded hashes and offered-snapshot versus received-copy diffs; earlier file contents are not retained. The memory inspector is read-only and returns each candidate in its own owner/conversation/namespace scope.

Offline scenarios (`offline_scenarios.py`) script only provider responses (and messages labelled `[scripted]`); scheduler reconstruction after restart uses the persisted scenario name and the same deterministic configuration. Live mode requires an explicit `LiveConfig` (DeepSeek only, explicit model, key supplied by the trusted launcher) and attaches a scheduler whose proposals await human review because no general acceptance rule exists. Live execution has not been validated against the real endpoint. `tui_runs` records which scheduler owns a root; a live root cannot be advanced from an offline session.

Remaining integrations include live allowed-provider validation, demonstrated autonomous multi-agent negotiation/allocation and plan revision, hard supervision beyond the Python code tool, internet search and retrieval, runtime Git operations, model-driven memory use and learning evaluation, and task-specific verification beyond exact text. A terminal control center now exists; it is not an authenticated multi-user interface. The mandatory course requirements remain the acceptance target; this foundation implements only part of their supporting infrastructure.
