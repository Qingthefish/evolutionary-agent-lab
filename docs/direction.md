# Direction and delivery scope

Status: implementation recommendation, not an instructor-issued rubric or an approved architecture.

## Primary authority

The instructor's final-project announcement defines the objective and mandatory boundaries. Personal experience and other courses are optional context. They must not replace required capabilities, change the model-provider restriction, or add unnecessary scope. Work is claimed per card through WeChat and the [Roadmap](team-roadmap.md); technical areas do not assign people.

Build a general multi-agent collaboration platform. Do not require selection of an industry vertical before starting. The unknown standardized test set makes general search, files, code, execution, and Git capabilities important.

## Recommended emphasis

Reliable execution with observable completion and bounded recovery. First cover every announcement requirement; then measure whether collaboration and experience memory improve results. Context compression, typed proof cards, and domain simulators are optional extensions, not core implementation commitments.

## Concrete development examples

1. Search official documentation, implement and test a small text-processing tool in isolated workspaces, write Markdown usage instructions, and commit/push to a designated test branch after any applicable approval.
2. Inspect an existing small repository, diagnose a failing test, repair the implementation, verify the result, and produce a change report.
3. Execute an ambiguous task, ask a concrete clarification, persist the response, and resume; separately exercise a critical operation requiring approval before execution.

These are development and demonstration tasks, not predictions of the instructor's test set. A platform-change assistant was an earlier candidate demonstration only; it is not the project objective.

## Proposed minimal design

- A coordinator and a small set of specialists with distinct tools, prompts, and private memory. Capabilities may be predefined, but task allocation, role negotiation, specialist delegation, and reassignment must occur at runtime rather than as a fixed script.
- A minimal text interface supporting private/group conversations, status, and human replies, plus a batch evaluation entry point.
- Enforced per-agent execution sandboxes and private file systems; explicit transfer of shared artifacts. A directory naming convention alone is insufficient.
- Durable task state, bounded retries, and verification of tool outputs. A model saying done is insufficient evidence of completion.
- Small persistent per-agent experience records: conditions, failure, attempted fix, verification, and provenance. Retrieve validated lessons for new tasks; do not reuse an old action authorization.
- DeepSeek or HKGAI adapter and a test double clearly restricted to offline engineering checks.

Implementation details remain provisional. More agents, a vector database, model training, complex negotiation protocols, and elaborate UI are not required by the announcement.

## Execution design agreed for the next implementation stages

The owner clarified these design priorities on 2026-10-15. They operationalize the announcement; they are not extra instructor requirements or claims that the runtime already implements them. README.md remains the implementation-status source.

- Decompose a high-level goal into deliverable-based subtasks with inputs, outputs, dependencies, and acceptance criteria. Check plan consistency, allow revision when missing steps are found, and invalidate affected downstream assumptions when the plan changes. Predefined specialties do not replace autonomous role negotiation, agent-to-agent delegation, or evidence-backed rework.
- Provide focused context for each step while retaining the global goal, active user constraints, relevant dependency results, applicable experience, and unresolved decisions. Allow retrieval of missing context. Narrow context is a budget choice, not permission to discard required evidence or a mandate to reproduce a compression paper.
- Let the model propose structured tool requests. Trusted program logic validates schemas, task ownership, authorization, and budgets before dispatch. Critical actions require applicable confirmation before effects; authorization must come from the right human and cannot be inferred from retrieved documents, memories, or another agent's assertion. Clarify ambiguity proactively and persist the response needed to resume the original task.
- Use actual artifact/tool results for acceptance. A verification agent may assist review, but deterministic checks use expectations independent of the candidate implementation wherever possible. Tests generated by the implementation itself are useful evidence, not sufficient proof of the entire goal. For reports and research outputs, identify automated checks separately from judgment that still requires human evaluation.
- On failure, return the specific error, failed step, relevant artifacts, and failed checks to the responsible agent. Bound step durations, retries, and the overall call/token budget. Stop on exhaustion or repeated lack of progress; retain partial artifacts and report blockers. Exhaustion is a terminal failure/partial outcome rather than successful completion, and it must not trigger indefinite human requests.
- Persist task/plan status and reconcile external effects before resuming. A stored status record alone cannot establish that a filesystem, sandbox, or Git effect did or did not occur after a crash. Code must run only inside an enforced process sandbox; there is no host-execution fallback.
- Keep experience private to each agent and within the applicable sharing/evaluation scope. Record observed conditions, failure, candidate repair, and verification provenance. Check applicability and retain contradictory or failed reuse evidence; do not treat an old repair or authorization as universally valid.
- Compare memory on/off and single/multi-agent execution using the same allowed model, comparable tools and budgets, matched tasks, consistent human-intervention rules, and controlled initial memory state. Record completion/time and supplementary call/token cost. Separate development from held-out tasks and obey official memory-reset/repeat-run rules. Do not assume collaboration or stored experience necessarily improves performance.

The complete acceptance target still includes private/group human interaction, independent per-agent sandboxes and filesystems, internet search, file CRUD, real code tests/execution, Git commit/push, Markdown/TXT documents, minimal UI, the allowed model provider, official test-set results, architecture/report/presentation, and continuous genuine contribution records.

## Current execution-backend decision

2026-10-16: implement an opt-in Docker Python backend as the first real process-execution path. It uses a trusted local Linux engine, digest-pinned official image, per-invocation private scratch space, non-root payload, resource/network restrictions, declared text exports, and explicit cleanup/recovery. The macOS development environment uses a separate Colima VM without host-directory or SSH-agent sharing. This is an implementation choice supporting R05/R08, not a new instructor requirement or confirmation of the minimum accepted sandbox boundary. It does not replace autonomous delegation or any other capability. See README.md for current evidence and [sandbox.md](sandbox.md) for operation details.

## Current coordination decision

2026-10-16: add a cooperative, durable task-tree scheduler around the existing runner/gateway. Trusted setup defines eligible role instructions/tools and independent acceptance policies; model tool proposals choose delegations at runtime. Wait for checked child results, share only explicitly offered artifacts, retain original constraints, and enforce root-wide limits at reservation boundaries. By default, terminal child failure still fails the root. The 2026-10-21 opt-in extension lets a parent explicitly replace a failed child with a bounded fresh attempt at the identical role/title/criteria, retaining failed history and shared budgets. It cannot skip denied/unreleased/unknown effects. Negotiation quality, general plan revision/dependency handling, and live-model behavior remain unvalidated. A fixed three-role development fixture exercises restart and handoff without claiming autonomous model ability. This is a staged implementation choice supporting the announcement, not an added grading requirement or a settled final architecture.

This is a substantial but bounded engineering project. Main uncertainties are provider tool-call behavior and quotas, local sandbox runtime, long-task reliability, and the unseen test distribution. Validate these early. README.md is the current implementation-status source; the architecture document describes the workflow contract. Offline workflow checks alone do not validate an execution sandbox or model integration.

Live-model validation requires an allowed provider credential. Offline fixtures can advance implementation but cannot establish completion rate or learning effectiveness. Sandbox implementation depends on available runtime support and the instructor's minimum boundary. No grade or universal task success is guaranteed by this plan.
